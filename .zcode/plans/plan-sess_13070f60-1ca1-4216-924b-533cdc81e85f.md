# 支持两年选题范围 + 前端渲染优化 + 后端稳定性增强

## 目标
- 时间范围从 90 天扩展到 **730 天（两年）**
- 保证一年以上高强度运行 10 次有 9 次稳定（90%+ 可靠性）
- Vercel 为主环境，不引入新依赖

---

## 第一部分：后端渐进分片抓取（稳定性核心）

### 问题
当前 `startProgressiveTopicFetch` 只做两阶段（7 天 + 完整天数），两年数据时第二阶段单次请求会串行翻大量页，远超 Vercel 超时（Pro 默认上限 300s）。`/api/tikhub/batch.ts` 也没有配 `maxDuration`。

### 方案：前端按月分片 + 逐片合并

**前端** `src/app/topicTimeWindow.ts`：
- 新增 `CHUNK_TOPIC_DAYS = 30`（每片 30 天）常量
- 新增 `chunkTopicRange(requestedDays, chunkDays)` → 返回 `number[]`，如 `chunkTopicRange(730, 30)` → `[7, 30, 30, ..., 30]`（第一片始终 7 天快速首屏，其余按 30 天切片）

**前端** `src/app/App.tsx` — 重写 `startProgressiveTopicFetch`：
- 改为**多阶段串行**：先拉第 1 片（7 天）→ 渲染 → 依次拉后续每片（30 天）→ 逐片 `mergeTopicBatchResults` 合并 + 渲染
- 每片之间检查 `generation`（取消机制已有），失败单片不影响已获取数据，记录到 `failedChunks` 供单独重试
- 新增 `failedChunks` 状态：存储失败的分片信息（起始天数），支持单独重试失败的分片而非全部重来
- 每片请求参数由 `topicRequestLimits(30)` 计算：`maxPages=min(60,max(20,ceil(30/7)*5))=25`, `count=min(1200,max(400,30*15))=450`，单片约 25 页 × ~2s/页 ≈ 50s，远在 Vercel 限制内

**后端** `api/_lib/topicPagination.js`：
- `MAX_RECENT_DAYS`: 90 → **730**
- `MAX_TOPIC_PAGES`: 60 → **100**（单片 30 天最多约 25 页，100 作为绝对安全上限）
- `MAX_TOPIC_VIDEOS`: 1200 → **2000**（单片上限仍够用，总计靠多片累积）

**后端** `api/tikhub/batch.ts`：
- 新增 `export const config = { maxDuration: 300 }`
- 错误消息 `"days must be an integer between 1 and 90"` → 用 `${MAX_RECENT_DAYS}` 动态拼接

**后端** `server/index.js` + `api/_lib/platformAdapters.js`：
- 同步更新硬编码 `"90"` 错误消息为 `${MAX_RECENT_DAYS}` 动态拼接

## 第三部分：前端渲染优化

### 问题
两年数据可能上千条选题，104 个分组。当前无虚拟列表、无 React.memo、内联 `.slice().sort()` 每次渲染重排。

### 方案：折叠 + IntersectionObserver 懒渲染 + 排序 memo 化

**App.tsx — 分组折叠策略调整**：
- 两年会产生 ~104 个分组。改为：**近 7 天默认展开，其余全部折叠**
- 当前已有 `expandedTopicGroups` 状态（默认 `[0]`），无需改逻辑，只确保新分组数下不展开过多

**App.tsx — 排序 memo 化**：
- 新增 `useMemo` 缓存每个分组的排序结果，依赖 `[topicGroups, sortKey]`
- 把当前内联的 `group.topics.slice().sort((a,b) => b.stats[sortKey] - a.stats[sortKey])` 从 JSX 中提取为 `sortedTopicGroups = useMemo(() => topicGroups.map(g => ({...g, topics: [...g.topics].sort(...)})), [topicGroups, sortKey])`
- 这样只有 `sortKey` 或 `topicGroups` 变化时才重排，勾选 topic 不再触发全量排序

**App.tsx — `selectedTopics` 查找优化**：
- 把 `selectedTopics: string[]` 的查找改为 `Set`：新增 `const selectedTopicIds = useMemo(() => new Set(selectedTopics), [selectedTopics])`
- 渲染时 `selectedTopicIds.has(topic.id)` 替代 `selectedTopics.includes(topic.id)`，O(1) 查找

**App.tsx — IntersectionObserver 懒渲染卡片**：
- 新增 `useLazyTopic` 自定义 hook：用 `IntersectionObserver` 监测每个 topic 卡片是否进入视口，只有进入视口才渲染完整卡片内容
- 默认渲染一个高度占位 div（`containIntrinsicSize: "0 180px"`），进入视口后才挂载完整内容
- 这保证即使展开一个含 200+ 条的分组，也只有视口内的 ~5-10 条卡片真正渲染

**App.tsx — `summarizeVideosResponse` 延迟执行**：
- 用 `useDeferredValue` 或在 `<details>` 的 `onToggle` 中才计算 `summarizeVideosResponse` + `JSON.stringify`，避免每次渲染都同步执行

**topicTimeWindow.ts — 时间戳缓存**：
- 在 `tikhubTopics` 的 useMemo 中，先对每个 topic 预计算 `timestampMs` 并缓存到 topic 对象上（`topic._tsMs`），后续 `groupTopicsByWeek` 和排序都读取该值，避免重复解析

## 第四部分：存储优化

**App.tsx — `persistTikhubResults` 改为 IndexedDB**：
- 两年数据 JSON 可能达 10-30MB，远超 sessionStorage 配额（通常 5-10MB）
- 当前已有 try/catch 兜底（超限则删除保持内存可用），但会导致刷新丢失
- 改为：优先尝试 sessionStorage（小数据量），失败时降级到只在内存保持（不改 IndexedDB，避免引入异步复杂度，保持改动范围可控）

**实际策略**：保持现有 try/catch 兜底不变（已正确处理配额超限），刷新后从内存重新请求即可。两年数据的持久化用渐进分片重新拉取，因为数据本身有时效性。

## 风险与缓解
- **Vercel 超时**：单片 30 天 ≈ 25 页 × 2s ≈ 50s，配 maxDuration 300s 有充足余量
- **前端卡顿**：IntersectionObserver + 排序 memo + Set 查找三管齐下，即使 1000+ 条也只渲染视口内卡片
- **数据丢失**：单片失败单独重试，不影响已获取的分片
- **向后兼容**：默认 7 天行为不变，只是上限从 90 扩到 730
